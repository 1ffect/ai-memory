整理 Claude Code 跨会话学习机制的六个模块，覆盖存储位置、触发条件、数据结构与已知限制。每条信息均标注来源。

📎 来源与方法论

  • 官方文档 — 来自 Anthropic 官方文档站 code.claude.com/docs/en/memory，可作为技术依据直接引用。

  • 未经证实 — 概念上合理、或散见于单一来源，但本文档整理过程中未能找到可交叉核实依据的细节。

MODULE 01

指令记忆 Instructional Memory — CLAUDE.md

用户手写的持久化指令文件。四个作用域，按优先级从低到高依次加载并拼接进上下文；三种内容扩展机制控制指令如何被组织与按需引入。

作用域与优先级 官方

作用域路径用途共享范围
managed 组织策略/etc/claude-code/CLAUDE.md（Linux/WSL）组织级强制规范机器上所有用户
user 用户级~/.claude/CLAUDE.md个人跨项目偏好仅本人（所有项目）
project 项目级./CLAUDE.md 或 ./.claude/CLAUDE.md团队共享的项目规范团队成员（经版本控制）
local 本地个人./CLAUDE.local.md个人项目级偏好，建议加入 .gitignore仅本人（当前项目）

加载顺序 = 优先级：从文件系统根目录到工作目录逐层拼接，同一目录下 CLAUDE.local.md 在 CLAUDE.md 之后追加。越晚加载的内容在上下文中越靠后，遵从优先级也越高。官方

三种扩展机制 官方

官方
递归 include — 使用 @path/to/file 语法导入其他文件，导入内容在启动时展开并加载；支持相对/绝对路径，最大递归深度 4 层。
代码块或反引号内的 @ 不会被当作导入语法解析。
官方
条件协议 — .claude/rules/ 目录下的规则文件可用 YAML frontmatter 中的 paths 字段限定生效范围，仅当 Claude 读取匹配路径的文件时才会加载该规则。
官方
嵌套挂载 — 工作目录及其上层目录中的 CLAUDE.md 在启动时加载；子目录中的 CLAUDE.md 不会预加载，而是在 Claude 实际读取该子目录下的文件时按需挂载。

路径作用域规则示例

---
paths:
  - "src/api/**/*.ts"
---

# API Development Rules
- All API endpoints must include input validation
- Use the standard error response format

双通道注入模型 非官方命名，功能层面成立

功能上可以理解为两条并行通道：通道 A（用户书写的 CLAUDE.md 指令层，作为系统提示之后的用户消息注入）与通道 B（系统自动维护的 memdir 行为规范层，见 Module 04）。这一命名并非 Anthropic 官方术语，但准确描述了两条独立数据管线的关系。

MODULE 02

短期记忆 Short-Term Memory — Conversation

当前会话的实时上下文窗口：完整的对话轮次、工具调用与工具返回结果。概念性描述

概念性
这是 Working Memory（任务）、Summary Memory（压缩）与 Long-Term Memory 提取三者共同的原始素材来源；本身不具备跨会话持久性，会话结束或被压缩后即不再以原始形式存在。

MODULE 03

工作记忆 Working Memory — Tasks

会话内的任务管理层，用于跟踪多步骤计划的执行状态。

泄露代码
对应泄露源码中的工具注册表条目：TaskCreate / TaskGet / TaskList / TaskUpdate / TaskStopTool。用于维护类似清单结构的任务状态，服务于当前会话的执行计划。
不写入 memdir，属于会话内瞬时状态，区别于跨会话持久化的长期记忆。

MODULE 04

长期记忆 Long-Term Memory — memdir

跨会话持久化的核心层，也是六模块中官方文档覆盖最完整的部分。

存储位置与目录结构 官方

~/.claude/projects/<project>/memory/ ├── MEMORY.md # 索引文件，每条记忆一行，每次会话开始时加载 ├── user_role.md # 单条记忆：用户角色/偏好 ├── feedback_testing.md # 单条记忆：某次纠正或确认的做法 └── ... # 其他主题文件，按需读取，不预加载

<project> 由 git 仓库推导，因此同一仓库的所有 worktree 与子目录共享同一个 memory 目录；不在 git 仓库内时使用项目根目录代替。官方

四种记忆类型 官方

type内容
user用户的角色、专业背景、工作偏好
feedback用户给出的纠正意见，以及被确认有效的做法
project无法从代码或 git 历史推导的进行中工作、截止日期、决策
reference指向项目之外信息的指针，例如工单系统、仪表盘

显式排除规则（信噪比控制）官方

Claude 会跳过任何可以从代码库直接推导的内容 —— 架构、文件路径、可通过 git 历史还原的调试修复 —— 以及 CLAUDE.md 中已经写明的内容。这是 memdir 保持高信噪比的核心机制：它只存放"从代码本身读不出来"的信息。

MEMORY.md 大小限制 官方

官方
每次会话开始时加载 MEMORY.md 的前 200 行或前 25KB（以先达到者为准）。超出部分不会被加载。写入后系统会检测文件是否接近或超出限制：接近限制时提示 Claude 精简（每条记忆一行、把细节移到主题文件、合并或删除过时条目）；超出限制时写入仍会成功，但系统会返回错误要求 Claude 重写索引，因为超出部分在下次加载时会被丢弃。

检索机制 泄露代码分析

泄露代码分析
主题文件不做向量嵌入检索。据分析文章披露的实现逻辑：系统扫描 memory 目录下所有非 MEMORY.md 的 .md 文件（上限 200 个），读取每个文件的前约 30 行提取 frontmatter 元数据，按修改时间排序后，将这些文件头交给一次独立的模型调用，由模型判断"哪些记忆明显对当前查询有用"（最多返回 5 个文件名），再读取被选中的主题文件全文。
即基于 AI 语义判断而非相似度检索/embedding，这也是为什么记忆标题的措辞需要覆盖未来提问可能使用的词汇，否则可能检索不到。

MODULE 05

摘要记忆 Summary Memory — Compression

对会话本身的压缩机制，用于回收上下文窗口空间，与 memdir 的持久化记忆是两套独立系统。

泄露代码
对应泄露源码中的 compact/ 模块。据分析文章描述，压缩存在分级：MicroCompact（轻量级）、AutoCompact（定期触发）、Full Compact（上下文压力较大时的完整压缩）。
分级细节未证实 三级压缩的具体触发阈值与实现差异未找到独立可核实来源，仅为多篇文章复述的名称。
官方
压缩后的持久化恢复：项目根目录的 CLAUDE.md 在 /compact 之后会被重新从磁盘读取并重新注入会话；子目录中的嵌套 CLAUDE.md 与带 paths: 的规则则在 Claude 之后重新读取匹配文件时才会重新加载。因此"压缩后指令丢失"通常是因为该指令只在对话中口头提过、位于尚未重新触发加载的嵌套文件中，或是一条尚未匹配到新文件的路径规则。

MODULE 06

休眠重构 Dormant Restructuring — AutoDream

后台离线整理机制，由主会话 fork 出的子代理执行，用于周期性梳理 memdir 内容。本模块内容主要来自泄露代码分析，未经 Anthropic 官方确认。

触发条件 — 双重门控 泄露代码分析

距上次整理 > 24 小时
AND
累计 ≥ 5 个新会话

两个条件需同时满足才会触发，避免整理过程过于频繁地打断使用。

四阶段流程

STAGE 1 标签未证实

定向探索：回顾近期会话记录与已有记忆文件，建立整理范围。

STAGE 2 标签未证实

信息收集：从会话记录中提炼可能值得写入的新事实。

STAGE 3 泄露代码

整合 Consolidate：写入记忆文件，将相对日期转换为绝对日期，删除相互矛盾的旧条目。

STAGE 4 泄露代码

剪枝 Prune：将 MEMORY.md 控制在 200 行 / 约 25KB 以内。

阶段 1、2 的具体名称为本文档基于多篇分析文章的整体流程描述归纳整理，实际源码中的确切命名未经逐字核实；阶段 3、4 的行为描述在多篇独立文章中一致出现，可信度相对更高。

权限与身份 泄露代码分析

泄露代码分析
整理代理拥有只读 shell 权限 —— 可以分析项目当前状态以核对记忆是否仍然准确，但无法修改项目文件，只能读写 memory 目录本身。

据分析文章引用，整理代理的系统提示词开篇即将任务定义为一次"梦境"式的反思过程：

"You are performing a dream — a reflective pass over your memory files."

（该引用来自第三方对泄露代码的分析文章，非 Anthropic 官方公开材料，一字不差的准确性未经独立核实。）

附属组件

与六模块并行运作的组件

以下组件不完全归入六模块框架，但属于同一套记忆/上下文系统的组成部分。

teamMemorySync 模块名确认

泄露源码目录结构中确认存在 teamMemorySync/ 模块。据相关描述，memory 目录下存在一个可选的 team/ 子目录，用于存放团队共享的知识，与个人记忆分开存放。

同步策略（如是否有服务器端权威副本）、冲突解决机制等具体实现细节 未证实。

子代理持久记忆 官方文档确认

子代理可通过配置中的 memory 字段维护自己独立、隔离的记忆目录，与主会话的 memdir 分开。主会话的 auto memory 默认不会加载进子代理。

例外：fork 类型的子代理会完整继承父会话的上下文与系统提示，因此也继承父会话已加载的记忆内容。

KAIROS 泄露代码 未发布

一个尚未发布的常驻后台特性标志，据报道在泄露源码中出现超过 150 次。设想中会让 Claude Code 从"被调用时才运行"转变为持续在后台观察项目、主动记录观察/决策/操作的常驻助手模式。截至本文整理时，未出现在任何公开发布版本中。

extractMemories 自动提取 模块名确认

会话完成后由 fork 出的子代理在后台运行，读取会话记录并写入 memdir 记忆文件。这与 AutoDream 是两个不同的写入者——一个在会话结束时即时运行，另一个按 24 小时/5 会话的双重门控周期性运行。

两者之间是否存在读写互斥、并发协调机制 未证实。

权限系统 泄露代码

每次工具调用都会经过权限检查层，根据配置的权限模式（default / plan / bypassPermissions / auto 等）自动放行、拒绝或向用户请求确认。

是否存在专门针对记忆文件的"路径安全防护"或"敏感数据审查"独立子系统 未找到具体实现依据，暂列为推测性描述。

Feature Flag 基础设施 泄露代码

基于 GrowthBook 的功能开关系统，配合 Bun 运行时的编译期死代码消除（dead code elimination），使得像 KAIROS 这样尚未上线的功能可以存在于源码仓库中，却不会被编译进面向用户的生产构建。
